# Команда и вычислительный план на пять дней

Редакция 25.11.2026. План согласован пользователем: 20 200 изображений, пять эпох, LR search и три seed A/M/B и LP. Всего 24 обучения: 12 LR + 12 final. REF и серии по рангам в обязательную работу не входят; время для них в текущем плане не резервируем.

Пять участников, весь код и архитектуру ведут пользователь с ассистентом. Двое без своих GPU могут запускать Colab. Сначала бесплатный Colab, после исчерпания доступного ресурса — RTX 4070 Ti, RTX 3090, RTX 3060. Платные вычисления не используем.

## Организация

| Работа | Исполнитель |
| --- | --- |
| Протокол, архитектура, код и исправления | пользователь + ассистент, одна версия |
| Colab | участники по готовому notebook и назначенным run ID |
| ПК после квот | владельцы трёх ПК, те же configs/manifests |
| Реестр | run ID, исполнитель, GPU, статус, ссылка на артефакты |
| Анализ | единый notebook, числа из завершённых runs |
| Литература, текст, слайды | можно распределить без разделения кода |

Участники не меняют настройки самостоятельно. Сбой сохраняют с логом; исправление делаем в общей версии. Один координатор — пользователь. assignments.json содержит run/attempt/device/profile/status и ссылку; одновременно одна активная попытка run. Результаты пишутся в Drive-папку владельца проекта executors/<executor_id>/runs/<run_id>/attempts/<attempt_id>; общий CSV собирается анализом. Данные читаются из локального HF cache. На ПК checkpoints постоянны локально, после run исполнитель вручную загружает готовые артефакты в общий Drive, приёмка проверяет hashes; для переноса незавершённого run передаётся epoch bundle; в Colab каждая эпоха обязана получить remote READY.

## Последовательность

1. Реализация и техническая проверка: несколько steps каждой конфигурации и короткий B-iso для памяти/скорости/сохранения/resume.
2. Двенадцать LR-проб на полном основном train/val: LP/A/M/B × {1e-4,1e-3,1e-2}, seed 142, пять эпох. Test loader не создаём.
3. Выбор LR отдельно для LP/A/M/B по val-2020, фиксация очереди final.
4. Девять final LoRA и три final LP: seeds 42,43,44, пять эпох, best checkpoint из пяти по val-2020.
5. Однократный test каждого из 12 best checkpoints, нормы LoRA, сбор результатов и анализ.

Полные предварительные обучения трёх методов для поиска длительности не проводим. Технические запуски и повторные попытки учитываем отдельно от 24 обучений. Правила границы сетки и невалидных проб определены в протоколе; автоматического расширения поиска нет.

## Colab и распределение GPU

Работаем через штатный PEFT и Transformers Trainer, без собственной реализации LoRA и распределённого обучения одной модели. Одна сессия выполняет один run за раз. Профиль выбираем до LR search по правилам [архитектуры](03-implementation.md): microbatch/accumulation 16/32, затем 8/64, затем 4/128 по OOM; если нужно, общий non-reentrant checkpointing для LoRA и повторная проверка. Effective batch512, AMP FP16, SDPA, TF32 off, num_workers=0. Выбираем первый профиль, прошедший проверку на самом маленьком участвующем устройстве; это ещё не измеренная вместимость.

[FAQ Colab](https://research.google.com/colaboratory/faq.html?hl=en): GPU/квоты меняются, ресурс не гарантирован, бесплатная сессия ограничена максимумом до 12 часов и может закончиться раньше. Файлы VM не постоянны. Пять участников не означают пять доступных GPU. Colab не включаем в гарантированный ресурс, доступные сессии уменьшают остаток работы для ПК.

Final назначаем четвёрками LP/A/M/B одного seed на одном устройстве по возможности. Порядок: seed42 LP→A→M→B, seed43 A→M→B→LP, seed44 M→B→LP→A. Для LR search предпочтителен один тип GPU; иначе блоки всех четырёх методов при одном LR с ротацией доступных устройств. Каждый исполнитель использует одну release-версию и общий runtime profile, не выбирает настройки самостоятельно. Незавершённый run можно перенести на другую GPU только с тем же кодом/профилем/версией данных и с записью всех сегментов; он исключается из сравнения стоимости с непрерывными, но не автоматически из accuracy.

Время сравниваем при одинаковых GPU/math/batch/workers/CPU/disk/cache условиях. Измеряем job wall, val, save/sync и train residual отдельно; GPU peak — общий train+val job, test в свежем процессе отдельно. Если условия различаются, фактические затраты публикуем с hardware, без точного рейтинга методов. Пять одновременно доступных GPU не предполагаются.

## Расчёт бюджета

Данные: **18 180 train / 2 020 val**, по 180/20 на класс. Test: 25 250. Все 24 обучения используют пять эпох:

| Работа | Число предъявлений изображений |
| --- | ---: |
| Train: 24 × 5 × 18 180 | 2 181 600 |
| Val: 24 × 5 × 2 020 | 242 400 |
| Test: 12 × 25 250 | 303 000 |

Пусть q — end-to-end train images/s (чтение/transforms/forward/backward/optimizer, без периодической val), v — inference images/s. Чистое время:

`T_hours = [2 181 600 / q + 545 400 / v] / 3 600`.

Все 24 run здесь оценены по стоимости LoRA, хотя LP обычно дешевле. Это упрощение, не верхняя граница расходов. Методы и GPU имеют разные скорости; после технического замера суммируем времена назначенных runs. Ниже **условные скорости, не benchmarks Colab или ваших карт**. Отношение v=4q также сценарное, после замера подставляем q и v независимо.

| Train q / inference v, изображений/с | Чистые GPU-часы | С резервом 30% |
| --- | ---: | ---: |
| 10 / 40 | 64,4 | 83,7 |
| 20 / 80 | 32,2 | 41,9 |
| 40 / 160 | 16,1 | 20,9 |

30% — условный запас на технические запуски/setup/sync/retries, не измеренные накладные расходы и не гарантия при множественных сбоях. Ожидание GPU расходует календарный срок, хотя не добавляет GPU-часов. Изначальные оценки 10–15 минут на run не используем.

При q=20/v=80 один run: около 77,9 минуты train+val, final test ещё 5,3 минуты. Обучение основной серии содержит примерно 36 updates/эпоху, 180/run при effective batch 512; фактический global_step проверяем. Пять эпох — общий ограниченный бюджет, не обещание схождения, автоматически его не увеличиваем.

Если после подготовки остаются три вычислительных дня, два ПК по 8 часов/день дают 48 GPU-часов, три — 72. Это условная доступность, не подтверждённое расписание. При v=4q расчёт с резервом помещается в 48 часов при q≈17,4 или быстрее, в 72 — при q≈11,6 или быстрее. На разных GPU учитываем время каждого задания, а не простое среднее скоростей.

## Календарь

| День | Цель | Контрольная точка |
| --- | --- | --- |
| 1 | Код, manifest, техническая проверка | модули/gradients, версии/batch, скорость, save/resume |
| 2 | LR search | 12 обработанных проб, выбран LR LP/A/M/B |
| 3 | Основные final runs | выполнение очереди из 12 final |
| 4 | Завершение final и test, резерв на сбои | 12 полных итоговых артефактов |
| 5 | Анализ, отчёт, слайды | воспроизводимые результаты и ограничения |

Это рабочая последовательность, не обещание квот. Дни 2–4 допускают параллельные независимые задания и перенос на ПК. Новые серии не начинаем. Если ресурс не соответствует расчёту, сначала пересматриваем расписание и доступность устройств. Согласованные данные, пять эпох и три seed не меняем незаметно; изменение требует новой версии протокола и учёта уже выполненных runs.

## Принятые правила хранения и отказов

Epoch bundle содержит текущий resume, совместимый с Trainer best_model, компактный best export, history/metadata/checksums. Локальное сохранение → новая постоянная папка → hashes → READY. Храним последние две подтверждённые версии и best; старые удаляем после проверки новой. В Colab три попытки remote sync, паузы 5 и 15 секунд; после отказа останавливаем обучение до следующей эпохи. На ПК подтверждённый локальный checkpoint позволяет продолжать, доставка в Drive контролируется до общей сборки.

Train/resume/evaluate/export — действия одного train.py. Ошибка test не требует нового обучения; повторяем оценку best. Test доступен только final после freeze выбранных LR и очереди. Все изображения модели не читаются с Drive на каждом batch; собственный сервер, Docker и очередь workers не нужны.

## Факты, которые нужно проверить в bootstrap

- VRAM/ОС и доступность трёх ПК, особенно модификацию RTX 3060.
- Владельца постоянного хранилища, объём и доступ участников.
- Практическую совместимость библиотек, вместимость batch, throughput и перенос checkpoints.

Методический источник — [гайд PEFT](https://huggingface.co/docs/peft/main/task_guides/image_classification_lora). Его воспроизведение не является этапом текущей серии. Источник истины по эксперименту — [02-protocol.md](02-protocol.md).
